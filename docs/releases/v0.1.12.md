# Ferrite v0.1.12

Patch release for Direct Order 27's alpha build, made on `release/0.1` from v0.1.11. It addresses the known issue
v0.1.10 left open: the frame time creeping up for as long as the game runs (DO27 session 2026-10-15 00:45, RX 7900 XTX,
RADV): `ferrite_vfx::runtime::upload_runtime_frame` went from 0.05 ms to 11.4 ms over 30 minutes while every other
system stayed flat.

- **Commit:** v0.1.12 = the tag `v0.1.12` (the gated code commit is named in the tag message).
- **Workspace version:** `0.1.12` (set by the release commit).
- **Branch:** `release/0.1` (alpha hotfixes). `main` is the post-alpha development line (batch v020); this release is merged forward into it.

## Upgrade from v0.1.11
No host source change. New, additive: `VfxGpu::curve_uploads`, `VfxGpu::queued_spawn_jobs`, `VfxGpu::note_upload`,
`CurveLut::upload_key`, `ferrite_vfx::gpu::STALE_UPLOADS`, `VfxScene::container_sizes` (`VfxSceneSizes`),
`VfxGpu::container_sizes` (`VfxGpuSizes`), `ferrite_core::profiling::thread_cpu_time`. Behaviour changes:
`VfxGpu::write_trails` stages the vertices and uploads them at the next `set_frame` (or `draw_trails`) instead of
writing the queue at once; a host that writes trails and then draws sees the same result.
`ferrite_vfx::glass::register_glass_effects` now runs before `tick_vfx_scene` (so before the runtime's upload): the
first curve-LUT upload already holds the glass curves instead of a second upload following it.

## The effects upload queues no GPU writes per frame (ADR-214)
What the DO27 log shows: the growth is per **update frame**, not per second and not hidden-specific. While the window
was drawn (00:51–01:03, ~35 fps) `upload_runtime_frame` grew 0.123 µs per frame; while the surfaces flapped hidden
(01:05–01:15, ~85–110 fps) 0.119 µs per frame. `tick_vfx_scene`, which walks the same effect instances, stayed at
0.02 ms, so the instance list did not grow. RSS grew about 10 KB per frame in both phases, while the GPU allocator's
total stayed flat (5399 MB for minutes), so no GPU memory leaked.

What the upload did every frame, besides CPU bookkeeping: it re-sent the whole, unchanged curve LUT (two
`queue.write_buffer` calls, each a new staging buffer, sized by the game's effect library: DO27 loads 44 effects) and
wrote the trail vertices straight to the queue. Spawn jobs waited for the next drawn frame.

Reproduced headlessly (`crates/ferrite_vfx/tests/frame_creep.rs`, the runtime's real `Update`, 25 effect instances,
up to 30 000 frames, lavapipe and an RTX 5090):
- **Hidden (no frame drawn):** the device's live allocations grew by **2 per frame** (4 219 at frame 2 000, 60 219 at
  30 000: the LUT's staging buffers, never submitted), RSS by about 4 KB per frame, and the spawn-job queue filled to
  its 65 536-job cap (then every push warned, and the next drawn frame would emit all of it at once).
- **Drawn every frame, or one in three:** flat on both drivers (allocations, RSS and the update cost).
- The update **cost** did not creep on lavapipe or NVIDIA in any mode. The 0.12 µs/frame growth on RADV is not
  reproduced here; no RADV device was reachable for this release (see Known).

Now (`ferrite_vfx`):
- `VfxGpu::write_curves` uploads a LUT only when it changed (`CurveLut::upload_key`: a per-LUT identity plus the
  append-only array lengths). In steady state the per-frame upload makes **no** `queue.write_buffer` call: the curve
  LUT goes up once per library change, trails and spawn jobs at the drawn frame.
- `write_trails` stages on the CPU; `set_frame` (or `draw_trails`) uploads.
- `VfxScene::upload` calls `VfxGpu::note_upload`; after `STALE_UPLOADS` (8) updates without a drawn frame, queued
  spawn jobs are dropped (one debug line per episode). At most one frame of jobs waits while hidden.
- Tests (`frame_creep.rs`): 5000 frames hidden and 5000 drawn; each asserts the device's live allocations at frame
  5000 are not above frame 500's, exactly one curve upload, no per-frame container grown between frame 1500 (steady
  population) and 5000 (scene: instance and GPU slots, pending jobs, death records within 10 %; GPU context:
  update-window history within its lifetime bound, spawn-job capacity, staged trails and decals, pipeline sets, free
  emitter slots), the update's cost at frames 4500–5000 within 10 % of a 3500-frame-younger twin's run beside it
  (below), and (hidden) fewer than 1024 queued spawn jobs. The diagnostic probes stay in the file (`--ignored`):
  `probe_queue_writes` (2 KiB, 1 KiB and a LUT-sized 32 KiB write per frame, with submit, poll or neither),
  `probe_hidden_updates`, `probe_rendered_updates`, `probe_drawn_growth`, `probe_hidden_growth` (every container
  and every system's time per window), `probe_detects_injected_creep`.

## The merge gate's `rendered_updates_stay_flat` failures (measurement, not the engine)
The first two v0.1.12 gates failed the drawn test's 10 % bound (wall time 230 → 264 µs; then "thread CPU time" from
`/proc/thread-self/schedstat`, 384 → 450 µs) with allocations flat; it reproduced unloaded on the 3080 box (110 →
147 µs). Measured on that box (`probe_drawn_growth`, `probe_hidden_growth`, 5000–10 000 frames):
- **Nothing grows.** Every container the update touches is flat from frame 1500 to 10 000 (death records ~8.2 k,
  update-window history 705, spawn jobs 0, staged trails 6, 25 GPU slots, 36 entities, 158 allocations), and so is
  every system under the engine's profiler (all systems 27.6 → 27.7 µs single-threaded; `upload_runtime_frame`
  7.4 → 7.7 µs, `tick_vfx_scene` 7.1 → 7.8 µs).
- **The clock was wrong.** The kernel updates `schedstat` only when the thread is switched out: it read 0 µs for a
  fixed 30 µs loop and for whole single-threaded updates. On the multi-threaded executor it counted what the main
  thread ran before its last park, and that share moved with the scheduler: the number rose 20 % with **no effect
  instance at all**. The test now uses `ferrite_core::profiling::thread_cpu_time` (`CLOCK_THREAD_CPUTIME_ID`) on
  the single-threaded executor, so the measured thread runs the whole update.
- **The scene's own rhythm.** Its 24 smoke columns sit at the 8192 smoke budget, so for a few hundred frames every
  ~7.7 s spawns are refused and the update is cheaper (17.5 µs against a flat 20.5 µs, hidden). The "best
  100-frame window" picked such a dip on one side only (+20 % on a flat series); the median of the five window
  medians does not. Before frame ~700 the population is still filling (the first window was cheaper still).
- **Load.** Thread CPU time still stretches when the machine fills (shared caches, SMT siblings, clocks): a 12-thread
  load ramp lifted the drawn update 10 % against its own earlier frames. The late cost is therefore compared with a
  **twin** of the same app, 3500 frames younger, on its own device, its frames interleaved one by one with the
  app's: load lands on both. Quiet: hidden −1.0/−1.1/−1.3 %, drawn +0.1/−0.7/+2.5 %; under the ramp: hidden
  −0.8/−1.3 %, drawn −1.0/−1.0 %. An injected creep of 16 ns a frame (the size the gate reported) reads +129 %
  (`probe_detects_injected_creep`).

## Known
- `frame_creep` measures what grows with an app's frames; growth in process-wide state (shared by the app and its
  twin) is not compared. It runs about 1500 frames longer than before (the twin).
- The creep's exact mechanism on RADV is unconfirmed. The fix removes every per-frame GPU call from the system that
  crept, so the same growth cannot recur there; confirm in the next DO27 session (`top_systems`:
  `upload_runtime_frame` should stay near 0.05 ms, RSS flat). To measure the driver itself, run
  `cargo test --release -p ferrite_vfx --test frame_creep probe_queue_writes -- --ignored --nocapture` on a RADV device.
- Flaky under load on the gate box (pass alone): `resize_memory`, `device_lost_exit[surface]`.
