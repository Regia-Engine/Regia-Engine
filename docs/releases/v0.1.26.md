# Ferrite v0.1.26

Builds on v0.1.25. A single-fix release: the compute-pool steal deadlock (ADR-303), a rare hang at client boot that
DO27 saw in about 1 of 20 starts.

## New

- Nothing new. The `ferrite_core::tasks` docs gain a "Locks" section with the rule below.

## Changed

- **No lock is held across a compute-pool fan-out** (ADR-303). The terrain height-pyramid snapshot, the
  `RenderedSurface` query, and the ground-bounce and scatter fan-outs read a snapshot, release the lock, then fan out.
  `TerrainGpu::with_height_mips` keeps its signature; its closure now runs with no lock held. Results are
  bit-identical to before, and no golden changed.
- A rendered-surface query that is running is no longer blocked by a publish or a crater edit, and it still reads the
  surface it started with. A crater while a long reader holds a snapshot costs one pyramid copy.

## Fixed

- **Compute-pool steal deadlock.** A thread waiting in a compute-pool scope can run an unrelated queued task. A lock
  held across that wait deadlocked when the stolen task took the same lock (terrain height pyramid, rendered surface).
  The engine now snapshots under the lock and fans out without it. The rule is documented in `ferrite_core::tasks`:
  never hold a lock across `scope`, `par_chunks` or `par_chunks_mut` that another pool task may take.

## Upgrade

- No format version changes and no API changes. Nothing to do for hosts.
- Game code that holds its own lock across a `ferrite_core::tasks` fan-out has the same hang. Copy what it needs and
  release the lock first.

## Known issues

- `pipeline_warm` leftover workers may still be inside the driver at normal quit under extreme load.
- macOS (not gated), on Apple M5: the `ferrite_editor hot_reload` fixture test and `ferrite_test_utils gpu_matches_cpu`
  (needs Sponza) fail; the rest pass.
- Code that fans out under some other lock is still a bug the type system does not catch.

Not in this release: baked light (reserved for v0.2.0).
