# Ferrite v0.1.23

Builds on v0.1.22. A stability and test-guard release: the material-graph worker shutdown fix, hardware guards for
lavapipe-blessed goldens, a wording cleanup, and a proposed KTX2 level-drop spec.

## New

- **Spec: KTX2 level drop** (ADR-271, proposed). `docs/specs/ktx2-level-drop.md` describes a
  `ferrite cook drop-levels` subcommand that removes the top N mip levels of an already-cooked KTX2 by copying the
  surviving level bytes unchanged, and the agent tool `assets.drop_levels` (dry run by default). No code yet;
  nothing is built until the owner answers the open questions in the spec (§ 11). No existing format hash moves.

## Changed

- **Lavapipe-blessed goldens on real GPUs** (ADR-270). `ferrite_test_utils::golden::compare_rgba8_to_png_on` keeps
  the given threshold exactly on software rasterizers and uses `min(threshold, 0.75)` SSIM on hardware, logging
  why. The affected tests use it, `sdr_sgsr_is_byte_identical_with_headroom_cleared` skips its byte compare on
  non-`Cpu` adapters, and the noon fog frame uses the same floor on hardware. A plain `cargo test --workspace` on a
  real GPU no longer shows the 15 hardware-baseline failures; a blank or wrong frame still fails. No golden is
  re-blessed.
- **Material-graph shutdown wait** (ADR-269). The limit for builds already inside the driver is 30 s (was 1 s);
  `FERRITE_MATGRAPH_SHUTDOWN_WAIT_MS` sets another limit in milliseconds. Dropping a renderer while graph
  materials are still compiling can take as long as the build in progress (usually well under a second; seconds on a
  loaded machine).
- Docs: shipped batch work is no longer labeled "v0.2.0"; v0.2.0 is reserved for baked light.

## Fixed

- **Crash at process exit in `lookdev warm_coverage` and other material-graph users** (ADR-269). Dropping a
  renderer used to wait 1 s for its material-graph workers and then leave one running inside
  `vkCreateGraphicsPipelines`; when the process exited, the NVIDIA shader compiler (driver 615.71.09) could crash.
  Builds that have not started are now dropped at once and builds already compiling are waited for, so workers are
  no longer abandoned inside the driver at exit. Evidence: 0 crashes in 120 launches under the load that crashed
  8 of 120 before. That is a measurement, not a proof.
- The device is never destroyed on a worker. The graph pipeline cache keeps one device clone until its workers are
  joined, waits for the GPU (at most 5 s) and releases the clone on the thread that drops the renderer. A worker
  could drop the last clone before, which ran `vkDestroyDevice` on the worker.

## Upgrade

Nothing to change. Hosts that depend on a renderer drop returning within 1 s should allow for the longer wait above.

## Known issues

- The macOS port passes 4979 of 5006 tests on an M5 (not gated); the failures are as listed for v0.1.22.
- The editor hot-reload fixture test (`hot_fixture_edits_keep_reflected_state`) fails on macOS.
- `pipeline_warm` leftover workers (`SHUTDOWN_WAIT` 2 s, `EXIT_WAIT` 5 s) can still be inside the driver at exit;
  ADR-269 does not cover them. The warm_coverage tests also drop their device without waiting for the GPU.

Not in this release: baked light (reserved for v0.2.0).
