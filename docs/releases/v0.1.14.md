# Ferrite v0.1.14

Patch release for Direct Order 27's alpha build, made on `release/0.1` from v0.1.13.1. Telemetry and knobs only (DO27's request of
2026-10-17): the hitch classifier stops reading a steady slow frame rate as hitches, the frame summary gains CPU/GPU bound, render
scale and GPU-wait fields, the perf overlay's GPU memory report leaves the frame thread, and the stochastic SSR roughness cutoff
becomes a knob. This release **adds API** (fields, functions, two agent methods) and changes the meaning of one option; it changes
no rendering default and no runner behaviour.

- **Commit:** v0.1.14 = the tag `v0.1.14` (the gated code commit is named in the tag message).
- **Workspace version:** `0.1.14`.
- **Branch:** `release/0.1` (alpha hotfixes). `main` is the post-alpha development line (batch v020); this release is merged forward into it.

## Upgrade from v0.1.13.1
No host source change is required: no struct the shell builds as a literal gained a field. New public items are additive
(`FrameBound`, `LiveFrame`, `Telemetry::live`, `ferrite_render::FrameWaits` / `frame_waits`, the SSSR cutoff functions); the new
structs are `#[non_exhaustive]` (read them, do not build them). One meaning changed: `TelemetryOptions::hitch_abs_ms` is now an excess
over the rolling median (see below). Full list: `book/user-guide/do27-host-checklist.md`, "Telemetry and knobs (v0.1.14)". ADR-222.

## A steady slow frame rate is not a hitch (ask 3)
Cause: a frame was a hitch when it was over 2 x the rolling median **or over 50 ms**. At a steady 66 ms every frame passed the second
test, and the token bucket (5 at once, then one per 2 s) let one through every 2 s: the "periodic 2 s hitch" in DO27's log was the
rate limit's pace, not a periodic stall.

Now a frame is a hitch when it is at least 8 ms and over 2 x the median **or more than 50 ms above the median**. Both tests are
relative. The burst, the rate limit and `hitches_suppressed` are unchanged. A step change (16 ms to 66 ms) still counts until the
63-frame median catches up (about 32 frames, mostly suppressed by the bucket); a steady loading screen at 300 ms is no longer a
string of severe hitches. Tests: steady 66 ms logs none; one 117 ms frame among 16 ms frames logs one; out of a steady 66 ms, a
140 ms frame (2.1 x) and a 120 ms frame (54 ms above) are hitches and a 100 ms frame is not; events plus suppressed equal the count.

`cpu_ms` (summary, hitch, perf overlay) is documented as what it is: `FrameRenderer::render_into` only, not the sim, extract, acquire
or present. Hitch records add `frame_ms_wall` (every main-thread phase of that frame) and `update_ms_wall` (`App::update` alone).

## Bound, render scale and GPU waits in the frame summary (asks 2 and 1, step S0)
New `ferrite::frame_summary` fields (`book/user-guide/telemetry.md`):
- `frame_bound`: `class` = `gpu_bound` when mean GPU time is at least 90 % of the mean frame interval, `cpu_bound` at 75 % or less,
  `balanced` between, `unknown` without GPU timing; `gpu_share`; per-frame counts of each class. The old `bound` field is unchanged.
- `render_scale_permille`: `last`, `mean`, `min`, `max` of the scale the renderer drew at (internal width x 1000 / output width).
  Not persisted.
- `wait_acquire_ms`, `wait_present_ms`, `wait_readback_ms`, `cpu_wait_on_gpu_ms` (`{mean, max}`): the main thread's waits on the GPU
  in `get_current_texture`, `Queue::present` and blocking screenshot readbacks. With the existing `frame_breakdown_ms`
  (`outside_update`, `render_split`) this is the measurement step S0 of the pipelined-rendering plan; the runner switch (S1) waits
  for DO27's numbers. New tracing spans `acquire` and `screenshot_readback` sit beside the existing `present`.
- `live`: the newest frame's values; the same as `Telemetry::live()` and the new agent method `telemetry.live`.

## Perf overlay: the memory report is off the frame thread (item 2)
Detailed mode called `memory_report` (an allocator block walk plus a `/proc` read) on the frame thread every 2 s. It now runs on a
short-lived `ferrite-perf-memory` thread, one at a time; the overlay shows the result at its next refresh. Test: a fake 400 ms report
leaves every overlay update under 100 ms and its numbers appear a few frames later.

## Stochastic SSR roughness cutoff knob (ask 7)
`ferrite_render::set_sssr_roughness_cutoff(v)` (clamped to 0.15..1; default unchanged, 0.55) and `FERRITE_SSSR_ROUGHNESS_CUTOFF=v`
(beats the setter, read once) set the perceptual roughness below which reflection rays are traced; the frame-skip test
(`material_may_be_glossy`) follows it. Agent: `render.get_sssr_cutoff`, `render.set_sssr_cutoff`. Not persisted. No golden changes:
the default uniform is bit-identical (unit test).

## Not verified here
GPU timings and the bound class on real hardware (this lane built and tested on lavapipe only), the wait fields on Wayland/Hyprland,
Android. The DO27 session on the owner's machine is the check for the hitch change and the S0 numbers.
