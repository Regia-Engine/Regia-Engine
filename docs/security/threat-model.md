# Threat model

Status: living document (ADR-3206). Line numbers are as of the commit that last regenerated this file, and they drift; the symbol beside each one is the stable reference. `crates/regia_core/tests/threat_model_doc.rs` checks that every cited file, symbol and test exists and that every row has a test or says why it has none.

This document says what the engine defends against, and against whom, and names the test behind each mitigation. It describes what was tested. It does not say that any part of the engine is free of faults, and it is not a list of every known gap: a finding that is not yet fixed is tracked until it is fixed, not published here.

Each test added by ADR-3206 was proved once by removing its mitigation locally and watching it fail. The older tests were read to confirm they assert the mitigation, and were not re-proved this way.

## Trusted by design

These are inside the boundary. The engine does not defend against them, and a game developer should not expect it to.

- **The person running the engine and processes of the same user.** They can read the agent token and the project.
- **A project's files.** A project is code. It decides the agent's permissions and output roots in `.regia/agent.toml`, and it names programs to run (`generators/*.toml`, `[editor] code_editor`, `[[tool]]`). Open and run only projects you trust, and treat an agent working in a project the way you treat that project.
- **Dynamic extensions and the hot-reload game library.** Same-build trusted code, running in the host process with its rights. Stamps and capabilities catch mistakes, not hostile code.
- **Third-party decoders and the Lua 5.1 implementation.** They are exercised by fuzzing where the engine reaches them, but their internals are not reviewed here.
- **The operating system, the compiler and the crates in `docs/03-workspace-and-dependencies.md`.** Dependency review is in ADR-2052.

## Boundaries

| # | Boundary | Attacker | What they control | What is at stake | Residual risk |
|---|---|---|---|---|---|
| 1 | [Agent WebSocket server and token](#1-agent-websocket-server-and-token) | A local process or user without the token; a web page in the owner's browser. | TCP connections to the port, handshake bytes, and JSON-RPC frames once authenticated. | Control of the running engine, and through it project files and the permissions the profile grants. | Any process of the same user can read the token file, so same-user code is not kept out. Holding every connection slot for a handshake deadline at a time still delays a real client. The client does not authenticate the server: a process that takes the port after a crash can answer an agent with false results. |
| 2 | [MCP over stdio and HTTP](#2-mcp-over-stdio-and-http) | For HTTP: a web page (DNS rebinding), a local process without the token, and under `--allow-remote` a host on the network. For stdio: nobody; the parent process is trusted. | HTTP requests: every header, the body, the number of connections. | A proxy holding the master token: every session has the project's whole profile. | `--allow-remote` speaks plain `http://`: the bearer token crosses the network in clear, so it belongs behind a tunnel or a TLS proxy. An owner's `--token-file` token may be as short as the check allows; there is no throttle on wrong tokens. |
| 3 | [Planted links in `.regia/agent/`](#3-planted-links-in-regiaagent) | A hostile repository or archive (git stores symbolic links), or another local user. | Whatever stands at `token`, `endpoint.json`, `audit.jsonl`, their temp names, and the folders above them, before the app starts. | Overwriting or appending to a file the link names, or sending a secret as a bearer token. | Owner-only modes exist on Unix only: on Windows the files take the folder's ACL, so the project folder has to be private. A link above the state folder is the user's own layout and is not checked. Same-user code is out of scope. |
| 4 | [Project files from a cloned repository](#4-project-files-from-a-cloned-repository) | The author of a repository the owner cloned. | Every file in it, including `.regia/agent.toml`, `generators/*.toml`, `Regia.toml`, and symbolic links. | The owner's account, environment and files. | A project is code. `.regia/agent.toml` is project configuration: it decides the agent's permissions and adds output roots, and project files name programs (`generators/*.toml`, `[editor] code_editor`, `[[tool]]`). Only run an agent or a generator on a project you trust. A name Windows aliases in other ways (`PROGRA~1`, case) still resolves under the root; the rule is about staying inside it. |
| 5 | [Mods, Workshop content and the Lua sandbox](#5-mods-workshop-content-and-the-lua-sandbox) | A mod or Workshop author. | Lua source, the mod's file tree, pak bytes, and which files override others. | Host files, process availability and game state. | Workshop content has no signature and no per-item prompt. C work between hook checks is uncharged until the next check. Mods see the entities the host binds to them. The Lua 5.1 implementation is part of the trusted base. |
| 6 | [Dynamic extensions and `[[tool]]` commands](#6-dynamic-extensions-and-tool-commands) | A repository author or an extension publisher. | The manifest, the library, the tool executable, and the `Regia.toml` keys that enable them. | The host process and the owner's account. | A tool has no OS isolation: with an empty environment it can still read the user's files. The library stamp catches a stale build, not a hostile one. |
| 7 | [Network packets and transport identity](#7-network-packets-and-transport-identity) | Anyone who can send a datagram to the server, forge a source address, or sit on the path; a hostile client. | Datagrams and source addresses. | Availability, passwords and tokens, and session integrity. | A client with no pin takes the key it is given on first use, which stops a listener and not an attacker on the path at that moment; pin the key where that matters. A plain `Deny` before keys exist can be forged. The volume of traffic is out of scope. |
| 8 | [Content delivery client and server](#8-content-delivery-client-and-server) | A CDN, a network attacker, a LAN client of `regia content serve`, or a local writer. | Response bytes, and the manifest when a host adopts a fetched one. | Mounted content, the disk, and files under the served root. | Manifests are not signed, so integrity rests on TLS and on where the host got its manifest. `regia content serve` is a development tool: no authentication, no rate limit, one thread per connection, and it serves what is in its root; do not expose it. Packaged files are trusted once installed. |
| 9 | [Save files, replays and demos](#9-save-files-replays-and-demos) | A shared or downloaded save, a synced saves folder, a crafted replay or demo, or an agent client choosing a path. | Every byte of the file, including its CRC. | Availability and the integrity of the world it loads into. | Nothing authenticates a save: a forged one loads, and a game must not treat a save as proof of anything. A registered component in a save is inserted like any other, so a game decides what it registers as saveable. |
| 10 | [Paks and cooked assets](#10-paks-and-cooked-assets) | A mod or Workshop author, or anyone who can change the files on disk. | Every byte of the file. | Memory, a process crash, and the integrity of content. | A pak's hash finds damage; it is unkeyed and excludes the table of contents, so it does not prove who made the file. An in-place cut of a mapped file while a view is served can still raise `SIGBUS` on POSIX; reads go through the file handle once the change is seen. Output is bounded per entry, not per pak. |
| 11 | [Importers](#11-importers) | Whoever supplies a shared source asset, or a project a user cooks or opens. | Source files, their side files, and their `.meta`. | Local files read into a build, and the availability of the cook host or the editor. | Importers run on an owner's machine over files the owner chose, so treat a cook of unknown content as running a tool on it. Third-party decoders are in the trusted base and are mostly exercised by no-panic fuzzing. Coverage of limits differs by format; a row below is what was tested for that format and no more. |
| 12 | [Crash upload and log scrubbing](#12-crash-upload-and-log-scrubbing) | A network observer, a hostile or compromised collector, or a local process planting files. | The network path, the server's replies, and the contents of `crash-*.txt`. | User names, paths, tokens, and the player's consent. | The scrubber is a list of patterns over text, applied where a row below says. It reduces what leaves; it does not prove nothing sensitive does. A game supplies the consent flag and the endpoint, and the engine ships no collector. `allow_cleartext` turns off the cleartext refusal. |
| 13 | [The DCC feed](#13-the-dcc-feed) | A local process, a web page, a LAN peer under `allow_remote`, or a hostile project's `Regia.toml`. | Frames, `hello` fields and texture paths. | The availability of the editor, scene integrity, and reads of project files. | There is no TLS, also under `allow_remote`. Same-user processes are effectively trusted: the Unix socket needs no token. An accepted peer can use a lot of memory within its limits. The feed is a development feature and is off unless the project turns it on. |
| 14 | [The hot-reload dylib](#14-the-hot-reload-dylib) | The author of the game crate, or anything that can write its sources. | Crate code, `build.rs`, `.cargo/config.toml`, and files under `.regia/hot`. | The editor process and the owner's account. | None of these checks is a defense against a hostile library: its initializers run when it is opened. `--game` builds and loads at once, and a change to the sources starts a rebuild with no prompt. |
| 15 | [`regia engine verify` and release trees](#15-regia-engine-verify-and-release-trees) | A mirror, a supply chain, or anyone who can write to the release tree. | Every file in the tree, and the manifest beside them. | Code that later runs on a game developer's machine and CI through Cargo builds. | The manifest travels with the tree and is not signed, so a tree and a manifest replaced together pass: this finds damage and partial replacement, and says nothing about who wrote the pair. An unlisted file is a warning. `verify` is a command to run, not a step of `regia new` or `upgrade-project`. There is no archive code: a release is unpacked with standard tools before `verify` sees it, so traversal, link entries and bombs in an archive are that tool's job. |

## Windows path rules

A level written on Linux gets opened on Windows, so a project path has to mean the same thing on both. The rule (`regia_core::project_path::check_relative`) is pure logic, so every host runs the same table: `crates/regia_core/tests/windows_path_rules.rs`. Each row goes through `check_relative`, `resolve_read`, `resolve_write` and `resolve_in_roots`.

| Input | Answer | `data.path_reason` |
|---|---|---|
| `C:\x`, `C:/x`, `C:x` | refused | `path_prefix` |
| `\\server\share`, `//server/share/x`, `\\?\C:\x`, `\\?\UNC\server\share\x`, `\\.\pipe\x` | refused | `path_absolute`; `path_remote` when absolute and outside every root on the host |
| `\x`, `/x` | refused | `path_absolute` |
| `..\x`, `a\..\..\b`, `a/..\..\b`, `.. \x`, `... \x` | refused | `path_parent` |
| `a.`, `a `, `file.txt.`, `dir./x`, `.regia /agent.toml` | refused: Windows can open such a name as another one | `path_trailing` |
| `file::$DATA`, `file:s`, `dir::$INDEX_ALLOCATION\x` | refused | `path_prefix` |
| `CON`, `NUL`, `COM1`, `LPT1`, `CON.txt`, `NUL.tar.gz`, `a\NUL`, `COM0`, `COM¹`, `LPT³`, `CONIN$` | refused, in any case | `path_device` |
| `a\b/c`, `.\a`, `console.txt`, `com10`, `nullable/x`, `..a`, `.regia/agent.toml` | accepted; `\` and `/` both separate | |

What Windows itself did with these names, run on one host (Windows build 26300, NTFS): the last segment loses its trailing dots and spaces, so `a.txt.`, `a.txt..` and `a.txt ` open `a.txt`, and a folder created as `sp ` is named `sp`. A middle segment loses one trailing dot, so `.regia./x` opens `.regia/x`; `.regia../x` and `.regia /x` did not open it. `.. `, `...` and `. .` did not reach the parent. A write to `a.txt:s` left `a.txt` unchanged. `NUL` was a device; `AUX`, `COM1`, `PRN`, `COM¹`, `CONIN$`, `nul.txt` and `CON.txt` under a full path were plain files there. `windows_opens_these_names_as_the_rule_says` holds the spellings that open another name, the stream and `NUL` on every Windows run; the rest is that one observation. The rule refuses more than that build needs, on purpose: Microsoft's naming documentation reserves the device names with any extension, other Windows versions were not run, and a file with such a name would not move between hosts.

Not covered by the rule: characters Windows refuses at open (`<>"|?*`, control characters) pass the check and fail at the open; 8.3 short names and case differences alias a name inside the root and stay inside it.

### One rule, and where it lives

Every helper in `regia_agent` that takes a project path goes through `regia_core::project_path`: `req_path` (`project_path_in`, `project_file_in`, `allowed_path_in`), `render_out` (`confine_path`, `confine_out_dir`, `resolve_under_roots`), `audio` (`confined_out_dir`, `project_file`), `mods::confine_mount_path`, `replay::confine_replay_path`, `demo` (`demo_path`, `save_path`), `fuzz::read_fixture`, `state_tree::read_project_text`, `ai_bt`, `anim_montage_edit`, `profiler::capture_path`, `terrain_heights::project_file` and `bake_export`. So do `regia_cli`'s release manifest and `regia_framework`'s extension manifests.

### Symbolic link races

The check holds when it runs: a process that can write inside the project and swaps a checked folder for a link before the caller's open can redirect that open (`a_folder_swapped_after_the_check_is_the_stated_limit`). The threat answered is a hostile path string; a concurrent writer inside the project is same-user code, which is trusted by design. `mods://` is stricter, because mods are not trusted: it re-walks the path, opens with `O_NOFOLLOW` and checks identity and hash on each read.
