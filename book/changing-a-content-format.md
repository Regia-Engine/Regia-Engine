# Changing a content format

A project owner who only needs to move files forward runs
[Content formats](how-to/create/content-formats.md): `regia upgrade-project` with no
`--write`, then the same command with `--write`. This page is the checklist for changing a
format's shape. Nothing in it changes the format's *current* shape.

Regia Engine's game content formats (`.material.ron`, `.level.ron`, `.prefab.ron`, `.ui.ron`,
`.vfx.ron`, `.animgraph.ron`, `.cue.ron`, `.audiopatch.ron`, `.terrain.layers.ron`, `.scatter.ron`,
`.meta`, save files and paks) are **frozen**: DO27's artists produce assets in them in parallel with
the engine, so a format must never change in a way that invalidates already-authored files. Every
format carries a `version` (or `format_version`) field, and a loader rejects a *newer* version with a
clear error and runs registered *migrators* for an older one (`docs/specs/12-assets.md` § 4a).
The steps below are the procedure for the day you need a new version.

## The rule

> A frozen format only changes together with a version bump **and** a migrator. A CI guard
> (`cargo xtask check-formats`) fails the build if a format's serde shape changed without a version
> bump, or if the version was bumped without a migrator registered from the previous version.

## Step by step

1. **Bump the version.** Change the format's `*_FORMAT_VERSION` constant (e.g.
   `MATERIAL_FORMAT_VERSION` in `regia_asset::material`) from 1 to 2.
2. **Add a migrator.** Register a `v1 → v2` step in the format's built-in migration chain (the
   `builtin_migrations()` table next to the loader), and add the same step to `regia
   upgrade-project`'s format registry in `crates/regia_cli/src/commands/upgrade_project.rs`.
   Every new field must have a default, so v1 files migrate without information loss.
3. **Add a fixture.** Put a checked-in v1 file in the format's `crates/*/tests/fixtures/` directory
   (hand-written, never generated by the current code) and a test that asserts it still loads.
4. **Record the new hash.** After the version bump, run `cargo xtask check-formats --update` to
   re-record the format's schema hash in `docs/formats/format-hashes.ron`. Commit that file.
5. **Make the old corpus fixture placeable.** An old corpus fixture must be placeable by `format_corpus_upgrade`: add its SUFFIX row (or a `WHOLE_NAME` / `COOKED_PAYLOAD` row) in `crates/regia_cli/tests/format_corpus_upgrade.rs` when its file name (`v1.ron`, `v1.bin`) lacks the suffix `upgrade-project` reads, and run `cargo test -p regia_cli --test format_corpus_upgrade`.

## The version contract

- **Loaders** read the version field first — before the full deserialize — reject a *newer* version
  with a clear "upgrade the engine" error even when the body no longer matches, and run the
  registered migration chain for an *older* version before validation
  (`regia_core::version::migrate` is the shared stepping loop).
- **`regia upgrade-project`** migrates on-disk files: without `--write` it lists every file and
  its version; with `--write` it rewrites files on an older version in place, keeping a `<file>.bak`.
  `--write` is two-phase (ADR-8811): every file and level directory is migrated first (files in
  memory, level directories in a staged copy); if any migrator fails, nothing in the project
  changes, no staged or `.bak` file is left, and the command exits non-zero listing every error.
  Only then are the migrated files staged next to their sources, the backups written and
  everything renamed into place.
  A run that is killed mid-way can leave a staging directory (`.<name>.<pid>.stage`); the
  upgrade plan and the cook never read it as a second copy of the level, the next dry run lists it
  ("--write would remove it") and the next `--write` removes it with a printed note (ADR-8861).
- **`cargo xtask check-formats`** hashes each format's serde field list — the root struct *and every
  nested struct* (its `schema_fingerprint()`) — and compares it to
  `docs/formats/format-hashes.ron`. A changed hash with an unchanged version is a build failure, and
  a version bump with no registered migrator from the previous version is a build failure too.

## Example: adding a field to `.material.ron`

To add an optional `emissive_strength` field to materials:

1. Add the field with `#[serde(default)]` to `StandardMaterialParams` in
   `crates/regia_asset/src/material.rs`.
2. Bump `MATERIAL_FORMAT_VERSION` to 2 and register a `v1 → v2` step in `builtin_migrations()`
   that sets `emissive_strength` to its default.
3. Update the `material` entry in `upgrade_project`'s registry so old projects migrate.
4. Add a v1 fixture (the existing `material.example.ron`) and a test that loads it as v1 and
   migrates it to v2.
5. Run `cargo xtask check-formats --update` and commit `format-hashes.ron`.

## The old-bytes corpus

`cargo xtask check-formats` hashes the *current* serde shape, so it cannot see a migrator that broke.
The promise that "the loader keeps reading every older layout" is checked with old bytes instead:
`crates/regia_agent/tests/fixtures/format-corpus/<format>/v<N>.<ext>` holds one fixture per version of
each frozen format, and the folder's `index.ron` records for each file its version, where the bytes came
from (`git <rev>:<path>`, `handwritten from <rev>`, or a frozen copy of the current registry fixture) and
what it exercises.

- **Old versions are real old bytes.** Take them from history (`git log -G'<CONST>: u32 = '`, then `git
  show <rev>:<path>` of a sample or test file), or hand-write them from the old struct at that revision and
  say so in `origin`. Never make an "old" fixture by running today's writer or by editing a version number.
- **The test.** `cargo test -p regia_agent --test format_corpus` loads every fixture through the fuzz-target
  registry's loaders and checks that it reaches the current version, that the re-encoding reads back equal,
  that migrating twice changes nothing, and that a copy patched to the current version + 1 is refused with an
  error naming the version (never a panic, never a silent load). Formats the registry cannot reach have the
  same test in their own crate. `cargo test -p regia_cli --test format_corpus_upgrade` runs
  `regia upgrade-project` over the old files.
- **The ratchet.** `cargo xtask check-formats` fails when a registered format has no corpus fixture for a
  version from v1 up to its current one, unless `docs/formats/format-corpus-exceptions.ron` lists that
  version with a reason.

When you bump a format, step 3 above therefore becomes: **keep** the fixture of the old current version,
**add** a `v<new>` fixture, add both to `index.ron`, and run the two tests above.

Blessing a missing current fixture is one serialized sequence — the bless tests of every crate share the one
corpus directory, so running them in parallel can snapshot `FROZEN.txt` or an `index.ron` half-written:

1. `REGIA_BLESS_FORMAT_CORPUS=1 cargo test -p regia_agent --test format_corpus bless_missing_current_fixtures -- --test-threads=1`
   writes the registry formats' current fixtures (a registry fixture already at the current version is copied, an
   older or versionless one is migrated by the loader, so the file is the current writer's output — never old
   bytes relabeled).
2. The own-crate bless tests, same env var, same single thread each — `regia_asset_pipeline`, `regia_asset`,
   `regia_animation`, `regia_cli`, `regia_script_lua`, `regia_xr` (`cargo test -p <crate> --test format_corpus
   bless -- --test-threads=1`; `regia_framework`, `regia_pt` and formats without a wired loader keep their
   hand-written or history-taken fixtures).
3. `REGIA_BLESS_FORMAT_CORPUS=1 cargo test -p regia_agent --test format_corpus bless_the_frozen_table -- --test-threads=1`
   **last**: it rewrites `FROZEN.txt` from the files on disk, adding new files and dropping entries whose file is
   gone (a renamed or deleted fixture must not stay listed).

A format with no wired loader at all cannot be blessed: list it in `docs/formats/format-corpus-exceptions.ron`
with the reason, and remove the entry when its fixture lands.

## One step per release

A release moves each frozen format **at most one version step** from the version the previous release shipped
(ADR-7724). If your format is still at its released version, a change of any kind, an optional defaulted field
included, bumps it by one with a migrator. If the format is already one step ahead on the line (bumped since the
last tag, so no released build has read that version), do not bump it again: fold your change into that unreleased
version. A fold must be additive for readers: every file the earlier shape of that version wrote still loads with the
same meaning (new optional or defaulted fields, new enum variants, an optional binary section the reader detects).
Keep the version's frozen corpus fixture byte for byte, add a second fixture of the same version
(`v<N>-<what>.<ext>`, a second `index.ron` entry) that uses the new part, make the migrator from the released version
write the final shape, and say "folded into v<N>" in your ADR. A change that cannot be additive waits for the next
release.

`cargo xtask check-formats` enforces this against the last release's table, `docs/formats/format-hashes-v0.7.0.ron`:
it fails when a released format changed its shape without a bump, moved two or more steps, went back, or left the
registry, even after `--update`. `cargo xtask check-formats --since-tag <tag-or-file>` checks against another release
(a git tag or a table file). At each minor release tag, commit that tag's `docs/formats/format-hashes.ron` as
`docs/formats/format-hashes-v<tag>.ron` and point `RELEASE_BASELINE` in `xtask/src/check_formats.rs` at it.
